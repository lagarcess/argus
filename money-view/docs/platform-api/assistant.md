# Contextual assistant and review checks

All paths prefix `/api/platform`. Financial answers select values from existing ledger, planning, investing and credit queries, with the same currency filters. Net worth uses ledger overview, including its canonical manual-investment adjustment. No assistant financial totals or recommendation engine. Every fact carries its original dated Evidence and page/filter/record target. Receipts are immutable snapshots: reopening history does not silently recalculate.

- `GET /assistant/actions` -> `{items:[spending,budget_review,net_worth,goal_progress,portfolio_review,credit_review],free_text_configured:boolean}`.
- `POST /assistant/ask` -> `{status:"answered"|"model_unavailable"|"unsupported",answer:null|Answer,conversation_id:null|string}`. Body `{action:"spending",parameters:{currency:"USD",month:"2026-09"},locale:"es-419",conversation_id?:string}` OR `{message:"...",parameters:{currency,month},locale,conversation_id?}`. Exactly one action/message. Optional `page` is read-only current-page context sent only when the user submits a question, never when opening the drawer. Prepared actions require no model. Free text only uses explicit CLARA_LLM_API_KEY, CLARA_LLM_BASE_URL, CLARA_LLM_MODEL; missing configuration returns model_unavailable without keyword routing. One semantic call, no retries. Active confirmed memories may inform semantic action interpretation, never overwrite financial records or save inferred memories.
- Answer: `{id,conversation_id,action,parameters,created_at,code:"grounded_records"|"no_records",interpretation:"prepared"|"semantic",facts:[{key,value:string,unit:"money"|"percent"|"count",currency:null|string,record_name:null|string,notes:["partial_unpriced_holdings" when applicable],source:Evidence,target:{page,query:{...},record_ids:[]}}]}`.
- `GET /assistant/conversations?state=active|archived|trashed&limit=20&offset=0` -> `{items:[Conversation],total,limit,offset}`. Default 20, limit 1..100, nonnegative offset. Total counts every matching household record; items use deterministic newest-first ordering. Conversation `{id,household_id,user_id,title,state,saved:boolean,created_at,updated_at}`.
- `GET /assistant/conversations/{id}?limit=10&offset=0` -> `{conversation,messages:[{id,role,text?,action?,answer_id?,created_at}],answers:[Answer],total,limit,offset}`. Total counts all answer turns. Default 10 latest complete turns, max 100; offset counts turns from newest. Each window displays complete receipts and their paired messages in original chronological order. No fact fields are trimmed.
- `PATCH /assistant/conversations/{id}` body any nonempty subset `{title:string,state:"active"|"archived"|"trashed",saved:boolean}` -> Conversation. Archive uses archived, trash uses trashed, restore uses active. Trashed/archived threads cannot receive questions until restored. Deletion is reversible until explicit household reset. Shared household conversation writes require editor/owner; household-scoped reads permitted to viewer.
- `GET /insights?currency=USD&month=2026-09` -> `{as_of,rubric:[...],checks:[Check],notices:[triggered Check]}`. Check `{id,code,triggered,state:"unread"|"read"|"dismissed",fact:Fact}`. Explicit rubric: `spending_exceeds_income: net < 0`, `budget_exceeded: remaining < 0`, `goal_fully_allocated: remaining <= 0`. Absence of a record means absence of a check, not a healthy score. No opaque score or advice. Stable notice identity includes fact value, target, period, excluding query timestamps and observation refresh dates.
- `PATCH /insights/{id}?currency=USD&month=2026-09` body `{state:"unread"|"read"|"dismissed"}` -> `{id,state}`. State is personal per household and persists; IDs must match a current triggered check in that context.

Integration: `initialize(store)`, `router`, `register_identity(identity)` or explicit `export_data(connection,context)`, `clear_data(connection,context)`, `usage_data(connection,context)` callbacks. Clear is permanent and only wired to explicit household reset; normal history controls use soft lifecycle. Tables all `p_assistant_*`, household scoped. No identity inferred from request payload.

Frontend `features/assistant/AssistantDrawer.tsx` exports `AssistantDrawer({locale,currency,page,onNavigate,onClose,onChanged,revision?})`; onNavigate `(page:Page,query?:Record<string,string>)=>void`. Opening only reads history/actions, does not send context or invoke a model. Prepared actions use explicit currency/month. Source links navigate to affected page/filter/record and close drawer. Prose is a bilingual prepared record explanation, not evidence of live model response quality.

Additional lifecycle endpoints:

- `POST /assistant/conversations/trash-all` `{confirmation:"TRASH HOUSEHOLD CONVERSATIONS"}` -> `{trashed:number,scope:"household",restorable:true}`. Owner only, all active/archived household conversations in one update, no first-page truncation. Repeat returns zero. Restore remains the ordinary PATCH.
- `GET /assistant/conversations/{id}/export` downloads `{schema_version:1,local_only:true,scope:"current_household",exported_at,conversation,messages,answers}`. Answer snapshots stay immutable; this is a local JSON download, no public link or public conversation-ID exposure.
- `GET /assistant/saved?limit=20&offset=0` -> `{items:[Conversation],total,limit,offset}` saved active/archived household conversations; trashed omitted. Same list bounds and exact matching count as history.
- `features/assistant/SavedAssistantPage.tsx` exports `SavedAssistantPage(PlatformPageProps)` for the saved route. Drawer accepts optional `initialConversationId` to reopen a saved conversation by reading its detail.

Verification: `tests/test_platform_assistant.py` exercises prepared canonical facts, bilingual/keyless no-keyword interpretation, mocked strict semantic responses, household boundaries, immutable snapshots after ledger change, history lifecycle, persisted personal notice state, bulk trash/export and registry reset. No live model/prose quality claim.


## Bounded execution and snapshots

`ask` dispatches synchronous `active_memories` and full `answer_question` work through `run_in_threadpool`. Financial queries run inside `Store.read_snapshot()`; `review_insights` shares one snapshot across spending, budgets, goals and current notice statuses. Nested domain reads reuse that snapshot. The fact snapshot exits before any immutable answer write begins. This avoids mixed financial observations without holding a database snapshot open during model HTTP calls.

Only configured semantic HTTP requests acquire `runtime.acquire_model(store,context)` in the threadpool. The lease is released from `finally`, also off-loop, with completed, failed, timeout or cancelled outcome. Prepared questions and keyless text do not consume admission. Overload returns the runtime's explicit HTTP 429 codes. `interpret` is the HTTP boundary and accepts `store/context`; actual HTTP without admission context fails closed. Explicit mocked transports may exercise schema handling independently in tests.

Limits fail explicitly rather than saving or returning partial facts: at most 500 selected facts per query, 256 KiB per new serialized receipt, 4 MiB of stored answer documents per requested window, 64 KiB of confirmed-memory context, and 10,000 total records / 8 MiB stored payload per complete assistant export. Codes are `assistant_fact_limit_exceeded`, `assistant_answer_too_large`, `assistant_window_too_large`, `assistant_context_too_large`, `assistant_export_too_large` (HTTP 413). Export preflight measures counts and byte lengths in SQL before materializing documents; the same cap applies to household export callbacks. A rejected new receipt rolls back all corresponding new conversation/message writes.

The drawer and Saved page expose previous/next list controls with real total counts. Open conversations expose older/newer complete answer windows. Local export errors remain visible in the drawer. Bulk trash still applies to every matching household row, never just the current page.

Scale-focused verification: 46 assistant tests pass, including event-loop progress during synchronous DB work, concurrent-write snapshot consistency across domains, bounded complete message/answer windows, exact list counts, oversized export/window failures with preserved immutable receipts, new-answer rollback, and model-admission completion/timeout/cancellation/rejection, including cancellation while atomic admission is still finishing. All model responses are mocked; these checks do not measure model quality or establish 10k-MAU hosting capacity.


Review follow-up: a supplied conversation target is checked for household ownership and active state before semantic memory/model work or prepared financial queries. The same state guard is rechecked under the answer write lock, so archiving during a query prevents appending a receipt. Assistant download transport uses the shared authenticated `requestResponse` owner, including session expiry handling. Shared button classes and `--p-line` supply both light and dark mode styling.

The deposit interpreter uses the same `runtime.model_admission` context manager at its HTTP boundary. Its explicit optional `admission=(store,context)` argument passes through fixture fallback only; exact prepared replay bypasses admission. No semantic prompt text changed. Combined assistant and deposit interpreter verification: 60 tests pass, all model responses mocked.

The focused browser regression `web/e2e/assistant-export.spec.ts` passed against the real drawer and shared authentication transport: after loaded financial facts, an export returning 401 `authentication_required` restores the login surface and removes the drawer and its answers. Full `bun run build` also passed after the shared-client integration. Runtime deadline fixtures use the typed `ModelLease.call_timeout_seconds`; both adapter test suites remain free of external model calls.
