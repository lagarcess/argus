- **Test-only, assertions not weakened.** Only line 219 changes (plus the comment at 216-217). The
  floor feeds two things: the early return (220) and the downward drag start

  clear the bar too), and the closing `XCTAssertTrue(element.isHittable)` (227) is unchanged. No
  test body changed. The helper can only scroll more. It never asserts less.
- **44 pt is measured, not guessed.** The probe hierarchy in `2026-10-04-w1f/feedback-keyboard-geometry.txt`
  has `Other ... {{0.0, 609.0}, {440.0, 44.0}}, label: 'Typing Predictions'` directly above
  `Keyboard ... {{0.0, 653.0}, ...}`. Drags starting 10/30/43 pt above the keyboard frame moved
  nothing. 51 pt moved Save 250 pt. Using a constant instead of the bar's localized label avoids a
  locale dependency.
- **Why the old code failed on Pro but passed on Pro Max.** With the old floor, start − barTop =
  (minY − 0.05H) − (minY − 44) = 44 − 0.05H. On the Pro (H 874) that is +0.3 pt, inside the bar on
  any keyboard height. On the Pro Max (H 956) it is −3.8 pt, just above the bar. With the fix, the
  start sits 0.05H above the bar top (43.7 pt Pro, 47.8 pt Pro Max). This fits the fix-run logs
  (`[0.50, 0.59]` ≈ y 561 on Pro Max) and the probe's 90 pt drag, which scrolled.

  on form content, so it still scrolls. The early return may be impossible to satisfy if the
  content cannot rise 44 pt above the keyboard. The loop then runs out after 10 drags and the
  final `isHittable` assert decides. That costs time, not a false failure. A hardware keyboard
  (no `app.keyboards`) takes the unchanged `app.frame.maxY - 100` path.
- **Bar taller than 44**: the 0.05H margin still puts the start above a bar up to ~88 pt (Pro) or ~92 pt
  (Pro Max). The early return could accept an element behind the part of the bar above 44 pt.
  Before the fix that window was the whole bar, so this is not a regression.
- **Could the higher start hit something interactive?** The drag is `press(forDuration: 0.01, thenDragTo:)`,
  a pan inside the ScrollView. A brief press that then moves does not fire a Button. The new start
  height on Pro Max (~561) is the same region the probe dragged from (563), which scrolled
  cleanly. Any accidental edit would be caught: the test asserts all three field values after
  the save (lines 32-36).
- **Callers** (lines 25, 88, 90, 91, 106, 164, 182, 188, 195; the helper is `private`, and no other
  file reads `keyboards.firstMatch.frame`). The keyboard is up only at 25 (Save after typing) and

- Out of scope (unchanged): the keyboard can exist off-screen while it animates in
