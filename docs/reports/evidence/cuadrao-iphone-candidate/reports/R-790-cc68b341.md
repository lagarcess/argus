## 1. Tap-target fixes

### Mechanism check

A `.buttonStyle(.plain)` Button or NavigationLink hit-tests only the drawn content of its label. The transparent area left by a `Spacer`, `.frame(...)` or padding is not hittable. `.contentShape(Rectangle())` placed after the label's last layout modifier makes the label's whole frame hittable. It changes no layout, typography, colour or artwork. Placed before `.accessibilityElement(children: .combine)`, it does not merge, duplicate or relabel accessibility elements. The tree already holds a precedent where content shape and row gestures coexist. `CuadraoUpdatesCanvas.swift:100-106,145` puts a content-shaped plain row together with `.swipeActions` and `.contextMenu`, so a content shape does not block swipe or context menus in this codebase.

## 3. Save shown disabled right after typing money: not a defect a person can hit

The ordering, traced through `Cuadrao/CanvasDecimalInput.swift`, `CanvasMoneyValueInput.swift` and `Planning/PlanAmountInput.swift`:

1. A keystroke calls `shouldChangeCharactersIn` on the main thread. It sets `coordinator.raw` and `field.text` synchronously (:106-109) and enqueues `commit` with `DispatchQueue.main.async` (:136-143, `pending += 1`).
2. In the same run-loop pass, before the before-waiting observers that run SwiftUI's update and the Core Animation commit, the main run loop services the main dispatch queue. So the block sets the `@State raw` binding and `pending` returns to 0 before the frame that first draws the new digit is committed.
3. The SwiftUI update runs `.onChange(of: raw)`, which sets `value = numericValue` (`CanvasMoneyValueInput.swift:23`). That writes `amount` or `exactShares[...]` and recomputes `.disabled(...)` (`CuadraoGroupExpenseEditor.swift:109`, :184) in the same update flush or the next one. At most, the enabled state appears one frame after the digit.
4. A tap fires its action on touch-up, which is a separate input event that arrives after the key's event has been handled. Main-queue blocks run in FIFO order, so the end-editing commit (:132) cannot overtake a keystroke commit. Both Save actions read SwiftUI state (`save(group,…)`, `amount` at :183), not the field.

Lost-digit paths I checked:

- `updateUIView` (:60-62) rewrites the field only when `pending == 0` and the binding differs. With FIFO commits, the binding equals `coordinator.raw` whenever `pending` is 0.
- The `onChange(of: value)` → `syncValue` reformat (:20-22) fires only when the numeric value differs. A newer keystroke's block cannot run in the middle of SwiftUI's synchronous update loop, so the reformat cannot overwrite the latest digit.
- The decimal pad has no return key and no `onSubmit` path.

**Conclusion.** This is a harness artefact, not an app defect. The XCUITest snapshot can read state from before the final insertion was delivered or reflected in accessibility. `92fa37bc`'s bounded wait is the right fix. Do not make `textFieldDidEndEditing` synchronous: end-editing commonly fires inside a SwiftUI update (focus change, sheet dismissal), which is the "Modifying state during view update" drop that `00b5be65` fixed. One honest limit: I traced this from code and did not measure it. W1c's proposed logging in `Coordinator.commit` would turn the trace into evidence if anyone wants it.
