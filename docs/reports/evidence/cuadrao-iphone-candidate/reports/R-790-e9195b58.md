# R-790: independent review of PR #790 at e9195b58

PR #790 "feat(cuadrao): add release UI and reconcile profile identity".
Head `e9195b587620d9611ef1f22d90c90975b03c48d6`, base integration `a8c37d3a` (merged at `ad0532f11`).
Read-only review of `git diff a8c37d3a...e9195b58`. No simulator was run. Two pure `swiftc` check
runners were run from a scratch copy of the pinned tree (results below).

## Verdict

Not ready as is. One release-gate break reaches every signed-in user in a release build (F1), and
it carries a second honesty problem with it (F2). The rest is limited-reach or nits. The merge
reconciliation, the locked deletion copy, the known-zero projection and the Household/auth
boundaries are clean.

## Findings

### F1 (P1, locked-decision break): release builds show photo selection in the connected Profile

- `ios/ArgusFoundation/ReleaseUI/Profile/CuadraoProfileIdentity.swift:100` (`PhotosPicker`), `:104` (Reposition photo)
- reached from `ios/ArgusFoundation/Connected/ConnectedCuadraoProfile.swift:27` and `:43`

`CuadraoIdentityEditor` shows "Elegir foto / Choose photo" with no `CuadraoFirstRelease.showsPersonalPhoto`
check. `ConnectedCuadraoProfile` presents that editor, and `ConnectedCuadraoRoot` shows
`ConnectedCuadraoShell` for every authenticated user in any build configuration. So a release build
offers photo selection, crop and a photo tab avatar.

This contradicts the PR's own recorded rule in three places: DESIGN.md lines 874 to 876 ("release
builds hide photo selection until hosted avatar storage is connected"), the MVEE Profile paragraph,
and the board's Trust and profile row 13 to 14. `docs/reports/evidence/784/README.md` item 4 also says
a release build shows no photo option.

Only the preview's picker (`CuadraoProfileAvatar.swift:31`) is gated. The test
`testReleaseGatesHideUnfinishedRowsAndPhotos` checks `cuadrao.profile.photo.choose` only, never
`release.avatar.photo`, so the gap is untested. The two editors duplicate the photo-load task, which is
how the gate landed on one and not the other.

Smallest fix: wrap the `PhotosPicker` and Reposition rows in
`if CuadraoFirstRelease.showsPersonalPhoto`, and add a `--cuadrao-release-gates` assertion that
`release.avatar.photo` is absent. The empty-state camera glyph (`CuadraoProfileIdentity.swift:38`)
also implies a photo in release and should follow the same gate.

### F2 (P2, honesty): connected avatar "Guardar / Save" is session-local and presented as saved

- `ios/ArgusFoundation/Connected/ConnectedCuadraoShell.swift:14` (`@State private var avatar`), `:85`
- `ios/ArgusFoundation/ReleaseUI/Profile/CuadraoProfileIdentity.swift:126`

In the connected app the selection lives in shell `@State`. It is lost on relaunch and on sign-out.
The editor's confirm action is labelled "Guardar / Save" and nothing tells the person it lasts only
for this session. DESIGN.md line 879 says the selection stays session-local until profile storage is
connected. The evidence README (items 13 to 14) says the same. A signed-in release user who picks
initials or a theme and taps Save sees it gone at next launch.

Smallest fix, one of: hide the connected "Editar avatar" entry in release until storage exists; or
keep initials and themes but relabel the action "Listo / Done" and add one line saying it applies on
this device for now. Founder call on which.

### F3 (P2, known-zero lock drift): `ReleaseRecordedMonth` ties "Sin datos" to "no records"

- `ios/ArgusFoundation/ReleaseUI/Updates/ReleaseUpdateModels.swift:71-72` (`case noRecords`)
- `ios/ArgusFoundation/ReleaseUI/Updates/ReleaseDataTruthViews.swift:12-14` ("Sin datos" + "No hay registros en este mes.")
- `ios/ArgusFoundation/ReleaseUI/Updates/ReleaseUpdatesGallery.swift:100` ("Mes sin registros")
- `ios/DesignPreviewTests/ReleaseUpdatesChecks.swift:10-11`

The October 2 Home comparisons lock (10:18 PM CT clarification) says "Sin datos" shows only when
coverage is missing, and it replaces the #787 reading that tied no data to a period with no records.
This shared component encodes the replaced reading: its only two states are "no records" and
"recorded amount", with no coverage input. A covered month with no expense rows has no honest
mapping. Today the component is reached only from the DEBUG gallery, so no release user sees it, but
the board hands it to the connected graft as the data-truth presentation. The evidence README row 10
("Missing month distinct from recorded zero") repeats the old wording.

The preview Home chart itself is correct (see Verified clean). This is the second model only.

Smallest fix: rename the case to missing coverage (`noCoverage`), change the copy to coverage wording,
rename the gallery heading and the two check messages.

## Verified clean

1. **Merge reconciliation.** At head, nothing outside the PR's own paths differs from `a8c37d3a`
   (`git diff --stat` over the rest of the tree is empty). No conflict markers. DESIGN.md loses only
   the `fc7650ea` external link (replaced by the in-repo dispositions section, which exists) and one
   retention sentence that was expanded, consistently with decisions 14, 15, 17 and 19. Board duplicate
   headings ("Acceptance and checkpoints", "Execution checklist and decision trail") already exist on
   base. Sign-in text matches decision 18. "Por correo" survives only as a removal comment and as
   "we don't send updates by email" copy.
2. **Release gating in the preview.** `CuadraoFirstRelease.hidesUnfinished` is `true` in release and
   argument-driven in DEBUG; the `--cuadrao-release-gates` string is inside `#if DEBUG`. Every Profile
   row goes through `shows(_:)` (root groups, nested links, Search memory perspective, bulk actions).
   No deep link, scene restoration or long-press path pushes a profile route. Photos in the preview:
   shown in DEBUG, hidden in release. `ReleaseUIReview`, all three galleries and the Home context-menu
   entry are `#if DEBUG`. Fixtures never advance to success on their own; success needs the explicit
   "Sample states / Result" menu. Memory copy in temporary chat follows `shows(.memory)`. Preview
   social sign-in stays off (`showsSocialSignIn = false`); connected buttons are #795's flag-gated ones.
3. **Deletion view.** Item 1 of the locked copy is byte-identical in Spanish and English (scripted
   comparison against the handoff). Member note and new-owner strings in `ReleaseUpdateCopy.swift` match
   items 2 and 3, including dropping the balance sentences when there is no open balance. `pending`
   (202, or 503 incomplete) shows "in progress" and never the finished state, matching API_CONTRACT and
   the web dialog wording. `failed` offers retry and claims nothing. Nothing on iOS calls
   `POST /account/delete`; the view has no release entry.
4. **Known zero in the Home preview.** `CanvasSpendingStory`: covered and empty is a known zero and
   shows 0.00 with the comparison as an amount; "Sin datos" only when not covered; first use and
   missing coverage give no zero and no comparison. Ran `run_home_balance.py` (80 passed) and
   `run_release_updates.py` (25 passed) from the pinned tree.
5. **Avatar ownership.** One `CuadraoAvatarSelection` feeds Profile and the tab in the preview, the
   connected shell and the review host. Connected selection resets when the profile id changes.
6. **Tests and script.** The welcome skip is keyed on `ARGUS_TEST_AUTH_UI_ENABLED`, with an honest
   reason, and the soft `if welcome exists` became a hard assert. The Mac pass `tests` step does run it
   in an auth-on build with `TEST_RUNNER_` forwarding and both social flags forced off. `verify.sh`
   uses `pipefail`, both invocations record status, and `build_app` now returns 1 on a failed build so
   `screens` fails. Photo tests lost their unconditional skips.
7. **Copy.** New strings have Spanish and English. No em dash in any added Swift line.
8. **Household, auth, session.** `HouseholdManagement` keeps the same command, URL scheme and
   `household.invite.share` / `.link` identifiers; it adds a QR and tint. No auth or session code changed.
