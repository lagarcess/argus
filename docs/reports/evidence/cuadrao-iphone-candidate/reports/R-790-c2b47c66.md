## 3. How six deletes could leave "40" (app code reading)

Order of events per keystroke (`CanvasDecimalInput.swift`):

1. `shouldChangeCharactersIn` (`:78-123`) synchronously sets `coordinator.raw`, sets `textField.text`, places the caret,
   and returns false. The field is therefore correct the instant the key is handled.
2. `commit` (`:136-144`) increments `pending` and queues the binding write on the main queue.
3. `updateUIView` (`:60-63`) rewrites the field only when `pending == 0` and the bound `raw` differs from
   `coordinator.raw`.

Inside `CanvasDecimalInput` alone I find no window: main-queue blocks run in order, so when `pending` reaches 0 the
bound value equals the last committed text. A rewrite then needs something else to write the bound `raw`. There are
three writers: `textFieldDidEndEditing`, `CanvasMoneyValueInput.onAppear`, and
`CanvasMoneyValueInput.onChange(of: value)` (`CanvasMoneyValueInput.swift:19-23`).

**The one real-looking window (unproven).** `CanvasMoneyValueInput` round-trips through the parent:
`onChange(of: raw)` writes `value`, and `onChange(of: value)` re-syncs `raw` from `value` when
`numericValue != value`. Trace, typing fast:

- Delete 4 lands: `raw = "40"`. Update runs, `onChange(of: raw)` sets `value = 40` (`exactShares` changes,
  `CuadraoGroupExpenseEditor.swift:82`).
- Before the update that reports the `value` change, delete 5's queued write lands: `raw = "4"`.
- The next update sees both changes. If the `value` action runs before the `raw` action, it compares
  `numericValue` 4 against `value` 40, calls `syncValue()`, and writes `raw = "40.00"`.
- If no key is in flight (`pending == 0`), `updateUIView` then sets the field to "40.00". The person's last delete is
  undone and decimals reappear.

Whether this can happen depends on two things I cannot establish by reading: whether SwiftUI applies the `value`
write and reports its change in the same main-loop turn (if so, no queued keystroke write can get in between), and the
order in which the two `onChange` actions run. **Unproven.**

**It does not explain the observed failure.** `syncValue` always writes two decimals. From this window the field ends
as "40.00" or "40.0", after which "300" is refused for too many decimals. The recording shows "400.00" -> "400.0" ->
"40" -> "403" -> "40,300". A plain "40" needs either a rewrite to "400.00" after the second delete (I found no path:
at "400." `value` and `raw` agree, and the row is in a non-lazy `VStack`, so `onAppear` does not refire), or two
deletes that never changed the text. For the second, one app-side candidate the author did not list: the silent early
return at `CanvasDecimalInput.swift:80` (`guard let r = Range(range, in: old) else { return false }`). If UIKit ever
passes a range computed against an earlier text length, the key is dropped with no error and no write. Also unproven.
The third candidate, synthesized deletes not delivered under load, is outside the app.

I agree with the author's account: class identified, mechanism not proven, 0 mismatches in 48 probed replacements.

**Could a person typing fast on a phone hit it?** The `onChange` window, if real, needs two keystrokes handled within
one update cycle. That is beyond normal thumb speed, but a main-thread stall of 100 ms or more queues taps and
delivers them back to back, so it cannot be ruled out. The result would be a visibly wrong amount in a money field.

## Findings

**P2 (outside this delta, unproven): `CanvasMoneyValueInput` can re-sync a focused field from a value it wrote itself.**
`ios/ArgusFoundation/Cuadrao/CanvasMoneyValueInput.swift:20-23`. Evidence: trace in section 3. Impact if real: a
keystroke is undone and the amount is reformatted while the person types. Smallest fix: remember the last value this
view wrote and skip the re-sync when the incoming value is that one.

```swift
@State private var written: Double?
.onChange(of: value) { _, _ in if value != written && numericValue != value { syncValue() } }
.onChange(of: raw) { _, _ in written = numericValue; value = numericValue }
```

External changes to `value` still re-sync. Not required to accept this delta; it should be decided with the keystroke
log the author proposes, since the observed "40" is not explained by it.

**P3-a: the Voice waits remove the test's sensitivity to a slow tray close.**
`CuadraoVoiceDesignUITests.swift:153, 184-194`. A close taking up to 3 s now passes. Smallest fix if wanted: record
the time from the close tap to `Escanear` leaving and fail above a stated limit (XCUITest polls non-existence about
once a second, so the limit cannot be tighter than about 1.5 s). Acceptable as is for this candidate.

**P3-b: silent key drop at `CanvasDecimalInput.swift:80`.** A refused keystroke leaves no trace. Smallest fix: a
DEBUG-only log line there, added together with the keystroke log the author already proposes.

**P3-c: README wording.** The README lists "the whole Group class once" among tries that did not reproduce the failure
without saying it ran with the read-back guard; W1h.md says it did (at `211b3d732`). One clause would make the guard's
only runtime proof explicit.
