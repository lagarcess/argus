# Account deletion FK census (Lane 6)

This census lists everything a plain `delete from auth.users` reaches in the Argus schema. Lane 6 ([handoff](mvee-five-lane-handoff.md#lane-6-account-deletion)) starts from it. It is the authoritative list of foreign keys for in-app account deletion and replaces the hand-read list in the handoff's "What exists today".

**Base:** `codex/private-alpha-next` at `bf6ccf85` (#788, Lane 1 backend), with all 108 migrations applied.

**Source:** two things produce it. A `pg_catalog` sweep finds every foreign key into `auth.users`, or into a table that `auth.users` reaches. A live probe then deletes a fully shared user against real PostgreSQL. Both run in [`tests/test_account_deletion_fk_census_postgres.py`](../../../tests/test_account_deletion_fk_census_postgres.py), with the sweep in [`tests/account_deletion_census.py`](../../../tests/account_deletion_census.py). CI runs them in the `guest-release-gates` real-PostgreSQL matrix. The first test fails when this document and the schema disagree, so a new migration that adds, drops or changes a key has to update the census in the same PR.

Nothing here deletes anyone. The probe runs inside a transaction that is always rolled back, and it adds no deletion command and no schema change.

## What a plain delete does today

A plain delete fails. The first error is the `retain_foreign_activity` trigger: *"surviving original owners retain canonical activity history"*. To find every later blocker, the probe lifts each one inside the rolled-back transaction and tries again. It took 21 lifts before the delete went through.

- **19 foreign keys block.** Eighteen are RESTRICT. One is NO ACTION and initially deferred, so it fires only at commit.
- **One trigger blocks:** `retain_foreign_activity` on `financial_activity_groups`.
- **One check blocks:** `households_check`. `households.admin_user_id` is ON DELETE SET NULL, but an active household must have an admin, so the SET NULL itself fails.

Eight more blocking-type keys had rows in the probes and never fired:

- **Six run between the person's own rows and go in the same cascade:** the three asset debt-link keys, `memory_records` → `memory_consent_actions` (seeded with a reconciliation still pending), `run_context_packets` → `context_packets` (from the guest probe), and the deferred `financial_activity_groups` → current revision.
- **Two restrict in the catalog, but their rows go first through another cascade:** `financial_goal_allocations.contributor_membership_id` goes through the person's own account, and `financial_plan_links` (`budget_id`, `user_id`) goes through the plan owner's `user_id`.

Lane 6 shouldn't rely on that order once it re-keys rows.

The rows B can see that a plain delete would destroy:

- **`financial_plan_links` (5).** `user_id` is the plan owner and cascades, so every claim in a shared plan the person owns goes, B's contributions included. Decision 17 step 5.2 moves those plans to the longest-standing participant. That has to happen **before** step 1's leave archive (Priya's #782 note 1), or the new owner gets a read-only archive.
- **`financial_goal_allocations` (3).** Backing from the person's accounts into B's goals cascades with the account, and so does B's backing of a goal the person owns.
- **`household_members` (2).** These cascade, but plan rows still restrict them. Step 5.1 keeps the membership row as the Exmiembro placeholder.
- **`household_account_grants` (4), `household_command_receipts` (7), `household_invitations` (3 set to null), `households` (1 set to null).** These are grants, idempotency receipts and invite ids. Step 1's leave and step 4 handle them explicitly.
- **`financial_activity_memberships` (1) and `financial_record_revisions` (1 removed, 1 set to null).** These are legs of cross-owner transfers. B's record that the person entered keeps its row, and `recorded_by` sets to null.

## What Lane 6 has to change before re-keying

Moving rows to a placeholder, or moving a plan to a new owner, means changing owner ids on keyed rows. The "Re-key to a placeholder" column says what each key needs. In short:

- **Keys straight to `auth.users`** (`financial_plan_definition_revisions.owner_id` and `actor_id`, `household_plan_receipts.actor_id`, and every `user_id` that cascades): a placeholder id has to be a real `auth.users` row, or the key has to change. `owner_id` and `household_plan_receipts.actor_id` are `not null`. `financial_plan_definition_revisions.actor_id` is nullable, so it can be set to null.
- **Composite owner keys** (`household_plan_bindings` to the plan definitions and `first_shared_revision` / `retained_revision`, `financial_plan_links`, `financial_goal_allocations` and `financial_goal_allocation_revisions` to accounts, goals and bindings, and the archive tables to `financial_activity_revisions`): every one is ON UPDATE NO ACTION and **not deferrable**. Neither side can change its owner id first. A plan transfer or a placeholder needs those keys made deferrable, or ON UPDATE CASCADE, in Lane 6's migration.
- **Membership keys** (`household_plan_participants`, `financial_plan_responsibilities`, `household_plan_receipts`, and the `contributor_membership_id` columns): these key on `household_members.id`, not on the user id. They can keep pointing at a placeholder membership row once `household_members.user_id` can be cleared. Today it's `not null` and ON DELETE CASCADE.
- **Deferrable keys:** only three are deferrable, all initially deferred: `financial_activity_memberships` → `financial_record_revisions` (the record-owner key), `financial_activity_groups` → its current revision, and `financial_record_revisions` reversal → `financial_activity_revisions`. They fire only at commit. A test that rolls back without `set constraints all immediate` never sees them.
- **ON UPDATE CASCADE:** only the two `conversation_read_states` keys use it.

## Outside the foreign keys

- **`financial_asset_changes.recorded_by`** holds a user id with no foreign key. If the person recorded a change on another owner's asset, their id stays on that row. Lane 6 clears it explicitly.
- **No foreign key reaches these tables, so a delete leaves them alone:** `checkpoints`, `checkpoint_blobs` and `checkpoint_writes`, keyed by conversation id as text (the guest probe confirms they survive). Also `argus_memory_vectors` (`payload` jsonb), `private_alpha_allowlist` (email), `private_alpha_access_welcome_claims` and `_deliveries` (recipient email), `guest_funnel_milestones` (`subject_key`), and `visitor_usage_counters` (`visitor_key`). Lane 6 decides for each one whether it identifies the person.
- **Supabase platform schemas** (`auth`, `storage`, `realtime` and the rest) are left out of the sweep, because their keys differ between the local Supabase stack and a vanilla PostgreSQL. Storage objects are step 3, after #778.
- **Lane 1's who-invited-whom record (#788) is in.** `invite_referrals` keeps `sender_ref`, a random uuid with no foreign key. The `invite_sender_refs` row that maps the person to it cascades, so the ref left behind identifies nobody. `beta_invitations.created_by` sets to null, so the person's unused beta invites and group links stay live and anonymous. The lane PR should decide whether to revoke them.
- **Not on this base yet:** account moves' locked history table (decision 14), and #778's Storage bucket. A migration that adds either one fails the census test until its rows are added here.

## Full census

Every foreign key into `auth.users`, or into a table `auth.users` reaches, grouped by area. "Plain delete, live probe" is what the probe saw:

- **Blocks:** the probe had to lift this key, with its number in the blockers list.
- **Cascades** or **sets to null:** the rows that went.
- **Inside the person's own cascade, doesn't block:** a blocking-type key whose rows went in the same delete.
- **Held:** its rows point at the person's rows that stayed, because the parent is shared or a blocker above held it.
- **Catalog only:** neither probe had rows here.

"Lane 6 must" cites the decision 17 steps in the [handoff](mvee-five-lane-handoff.md#steps-in-order).

## How the probe works

The fixture reuses the Household fixtures under `tests/household/`. Their real services build:

- **Household 1:** A is admin and B is a member. Account grants run both ways.
- **Plans A owns, shared with B:** a budget, a bill, a goal and a debt. B pays into the budget, the bill and the goal, and backs A's goal from B's own account.
- **Plans B owns, shared with A:** a bill and a goal. A pays into both, backs B's goal, and carries a 50% responsibility in each.
- **A #773 archive on a plan A owns:** C joins household 1, pays into a bill A owns, and leaves.
- **Household 2:** B is admin. A joins, pays into B's bill, backs B's goal, and leaves, so departure archives pin A's activity under B's binding.
- **A's own rows:** a Plaid connection, an asset linked to one debt and then re-linked to another, a profile, a conversation and message, an account-deletion feedback row, and a full memory graph with a reconciliation still pending.

A second probe deletes a guest with the whole chat, research, route-receipt and cost-ledger graph from the guest cleanup tests. It goes through with no blocker.

The probe runs `set constraints all immediate`, deletes A, and records each error. Then it lifts that one constraint, trigger or check inside the transaction and tries again until the delete goes through. Finally it compares every table before and after, and rolls everything back.

To regenerate the rows after a migration, point `ARGUS_DISPOSABLE_DATABASE_URL` at a migrated disposable database and run `python -m tests.account_deletion_census`. It prints the sweep columns with the last two cells as `TODO`. Fill those cells in from the test's report, which it writes to `temp/account-deletion-fk-census-report.md`.
